# Text Modernisation Layer Proposal

## Purpose

The site should offer two reading views:

- **Original**: the corrected transcription, preserving the wording, spelling,
  punctuation, capitalization, and numbering of the printed edition.
- **Modernised**: the same transcription with a small, explicitly edited set of
  presentational substitutions, such as `Chap. I` becoming `Chapter 1`.

The original view remains the authoritative edition. Modernisation is a reading
aid, not a second transcription, and must not silently change the historical
record.

## Recommendation

Store the original text as the literal text content of the HTML. Add a
`data-modern` attribute only to a phrase for which a modern display form has
been approved:

```html
<h3><span data-modern="Chapter 1">CHAP. I.</span></h3>
```

In the original view, the browser displays `CHAP. I.`. In the modernised view,
shared JavaScript replaces that span's displayed text with `Chapter 1`. The
script retains the original value in memory and restores it when the reader
switches back.

This duplicates only the short phrases that differ, not paragraphs, chapters,
or pages. The HTML source, no-JavaScript experience, and default indexed text
all remain verbatim.

## Why This Model

### Canonical text stays visible in the source

The historical transcription is not hidden in an attribute, generated by
JavaScript, or maintained in a separate file. A browser without JavaScript
receives the complete original edition.

### Changes are local and reviewable

Each modernisation sits beside its source phrase. A reviewer can inspect:

```html
<span data-modern="Chapter 1">CHAP. I.</span>
```

without consulting a second document or matching offsets into a large text
file. A repository search for `data-modern` produces the full modernisation
inventory.

### Existing semantics are preserved

The annotation is an inline `<span>` and does not alter heading, paragraph,
quotation, emphasis, link, or footnote semantics. The span should wrap the
smallest complete phrase that can be safely replaced.

### It supports progressive enhancement

Original text is the default. If the script fails, storage is unavailable, or
CSS does not load, the reader still gets a complete and usable book.

## Reader Interface

Add one edition control to the shared page shell:

```html
<fieldset class="text-view-control">
  <legend>Text view</legend>
  <label>
    <input type="radio" name="text-view" value="original" checked>
    Original
  </label>
  <label>
    <input type="radio" name="text-view" value="modern">
    Modernised
  </label>
</fieldset>
```

The control should appear in the top bar or reading-card header and be rendered
only on pages containing book text. Radio buttons are preferable to an
ambiguous on/off switch because both available states are named.

The shared script in `assets/site.js` should:

1. Find every element with a `data-modern` attribute.
2. Record its original `textContent` before making any replacement.
3. Apply either the original or modern value to all annotated elements.
4. Update the radio control and set `data-text-view` on `<html>`.
5. Save the reader's preference in `localStorage`.
6. Use `original` when there is no saved preference or storage is unavailable.

The preference should apply across book pages. The control must work by
keyboard, retain normal visible focus styles, and have a programmatic legend.
No live-region announcement is needed because the selected radio state already
communicates the change.

## URL And Citation Behaviour

The URL should optionally accept `?view=original` or `?view=modern`. An explicit
URL value takes precedence over the stored preference for that page load. This
makes a modernised view shareable without changing the canonical document.

The query parameter must not be added during ordinary switching; doing so would
create unnecessary history entries and duplicate crawlable URLs. If canonical
link metadata is later introduced, it should point to the URL without the view
parameter.

The page should identify the active mode near the control. Readers citing the
book should be advised that the original view is authoritative and that the
modernised wording is editorial.

## Editorial Scope

The first release should be deliberately conservative. Suitable changes
include:

- expanded structural abbreviations: `CHAP.` to `Chapter`;
- Arabic display of chapter numbers: `I` to `1`;
- clearer labels for tables, references, or divisions where the meaning is
  certain;
- normalized display of purely navigational or structural wording.

The layer should not initially modernise:

- spelling or word choice in prose;
- punctuation within prose;
- personal names, place names, titles, quotations, or Latin;
- dates, measurements, money, or other values;
- footnote text or note-reference labels;
- uncertain OCR readings.

Those changes carry interpretive risk and would need a separately defined
editorial policy. OCR corrections belong in the canonical transcription, not
in the modernisation layer.

Capitalization may be modernised as part of an approved structural label, as in
`CHAP. I.` to `Chapter 1`. CSS should not be used to disguise a textual change.

## Annotation Rules

- Use `data-modern` only when the modern value differs from the original.
- Keep the original value as the element's literal text content.
- Wrap the smallest meaningful phrase, but do not split a replacement across
  multiple annotated elements.
- Do not place interactive content such as links or footnote references inside
  a replaceable span.
- Do not put HTML in `data-modern`; modern values are plain text and must be
  assigned with `textContent`.
- Do not annotate OCR mistakes. Correct those in the original transcription and
  record them in the OCR correction log.
- Treat every annotation as an editorial assertion requiring review.

If a proposed modernisation needs emphasis, links, ruby text, or other nested
markup, it is outside the first version of this scheme and should be reviewed
separately.

## Audit Trail

The annotations are self-locating, but an exported inventory should be
generated for editorial review. A validation script should scan `text/*.html`
and produce or verify a table containing:

- file;
- nearest heading or stable element ID;
- original text;
- modern text.

The generated inventory should not become the source of the replacements; the
HTML remains the source. It can be committed as a review artefact if the
project wants a human-readable change register.

The validator should fail when:

- `data-modern` is empty or equals the original text;
- an annotated element contains child elements;
- an annotated element contains no original text;
- a modernisation appears outside a book article without an explicit
  exception;
- the same edition-control ID occurs more than once on a page.

## Styling And Printing

The control should follow the existing site design and remain visually
secondary to the book text. A short label such as `Editorial modernisation`
should be available as help text.

Printing should default to the view currently selected by the reader, with a
small generated or static notice stating either `Original transcription` or
`Modernised reading view`. The text itself must not show both variants at once.

## Alternatives Considered

### Duplicate complete documents

Separate original and modern HTML files make each version simple to render, but
they double the text, allow corrections to drift, complicate anchors and
footnotes, and make review unnecessarily difficult.

### CSS generated content

Hiding original text and injecting replacements with `::before` or
`content: attr(...)` is unreliable for accessibility, text selection, copying,
searching, and printing. CSS should control presentation, not supply edition
text.

### Two child spans per replacement

Keeping original and modern strings in separate child elements permits
CSS-only switching, but both variants enter the document tree and require
careful hiding from assistive technology. It also duplicates markup and creates
poor copy-and-search behaviour.

### A separate JSON replacement file

A JSON dictionary keeps HTML clean but makes replacements difficult to locate
and review. Matching by source string is ambiguous, while matching by element
ID creates a second synchronized data model. JSON may be useful for a generated
audit export, but not as the editorial source.

### Automatic linguistic modernisation

Runtime rules or broad search-and-replace cannot reliably distinguish headings,
quotations, names, abbreviations, and prose. Modernisations should be explicit
annotations reviewed in context.

## Delivery Plan

### Phase 1: Proof of concept

- Add the reader control and switching logic to the shared shell.
- Annotate a small set of chapter labels, beginning with `CHAP. I.`.
- Confirm keyboard, screen-reader, copy, find, print, and no-JavaScript
  behaviour.
- Add automated validation for the annotation rules.

### Phase 2: Structural labels

- Inventory chapter, part, reference, and table labels across converted pages.
- Agree each replacement pair before applying it.
- Add annotations and review the generated inventory.

### Phase 3: Consider broader modernisation

- Gather reader feedback.
- Define a separate editorial policy before changing historical prose.
- Expand only if each class of change can be applied consistently and audited.

## Acceptance Criteria

- The unmodified HTML response contains the complete original transcription.
- Disabling JavaScript leaves the original edition readable.
- Switching views never changes links, IDs, footnote targets, or document
  structure.
- The reader's choice persists across book pages.
- `?view=original` and `?view=modern` select a predictable initial view.
- Copying or searching text uses only the currently displayed variant.
- Every modernised phrase is discoverable with a repository search and appears
  in the generated audit inventory.
- Existing OCR correction records remain separate from editorial
  modernisations.

## Decision Requested

Approve the annotated-source model for a small proof of concept limited to
structural labels. This tests the interaction and editorial workflow without
committing the project to prose modernisation or a second full-text edition.
